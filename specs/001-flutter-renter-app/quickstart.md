# Quickstart: Validating the Ziyam SelfDrive Mobile App

## Prerequisites

- Flutter SDK installed (already present on this machine at `C:\Users\8line\flutter`).
- `src/backend` running locally against a PostgreSQL instance with `prisma migrate` applied, and
  the itinerary/booking PayU sandbox credentials already configured (same `.env` the web app uses
  — no new secrets for this app).
- Firebase project config files (`google-services.json`, `GoogleService-Info.plist`) placed by the
  project owner under `mobile/android/app/` and `mobile/ios/Runner/` respectively (see
  `contracts/firebase-ai-itinerary.md`) — not generated by this quickstart.

## Setup

```bash
cd mobile
flutter pub get
flutterfire configure   # once, against the same Firebase project as src/frontend
flutter run              # against a device/emulator, API base URL pointed at local src/backend
```

## Scenario 1 — Discover the fleet (Story 1 / FR-001–FR-003)

1. Launch the app on a fresh install (no stored session).
2. Sign up with a new email/phone.
3. Confirm the app lands on the fleet browse screen, already authenticated.
4. Search a category (e.g. "SUV") and open a car's detail page.

**Expected**: results match what `GET /cars?category=SUV` returns from the same backend the web
app uses; the car detail screen shows price, specs, and current availability.

## Scenario 2 — Book and pay (Story 2 / FR-004–FR-008, SC-003)

1. From a car detail screen, select a valid date range.
2. Confirm price + security deposit are shown before payment.
3. Complete payment through the in-app WebView (PayU sandbox).
4. Confirm the booking appears as confirmed (instant-book) or pending (request-to-book).
5. **Concurrency check**: from two devices/sessions, submit overlapping-date bookings for the same
   car at nearly the same time. Exactly one must succeed; the other must be told the dates are no
   longer available. This proves the required `prisma.$transaction` fix in
   `booking.routes.ts` (see research.md) rather than just exercising the happy path.

## Scenario 3 — AI itinerary (Story 3 / FR-009–FR-010, SC-004)

1. From the itinerary entry point, pick a destination (Ooty/Coorg/Chikmagalur/Gokarna).
2. Pay via the same WebView flow.
3. Confirm a "generating" state appears, then the itinerary renders.
4. Force-quit and reopen the app; reopen the same itinerary — content must appear immediately with
   no new charge and no regeneration call.
5. (Failure-path check) Temporarily block the Firebase AI Logic call after a successful payment;
   confirm the paid unlock is preserved and a retry (without re-paying) succeeds once unblocked.

## Scenario 4 — Profile & KYC (Story 4 / FR-011–FR-012)

1. Open Profile, edit a field (e.g. phone number placeholder text — not a real number in test data),
   save, reopen the screen, confirm it persisted.
2. Open KYC status — confirm only a verification state (pending/verified/rejected) is shown, and
   that no raw Aadhaar/PAN/DL number or the account's `kycDocUrl` ever appears anywhere on screen.

## Cross-cutting checks (FR-013, FR-014, SC-005)

- Attempt to fetch another account's booking/profile using a guessed or reused id while logged in
  as a different user — must be denied.
- Put the device in airplane mode mid-flow on each screen above — must show a clear error/offline
  state, never a crash, and never silently discard an in-progress form.
- Review every screen touching `User`/`kycDocUrl`/booking `coDriverLicenseNumber` for unmasked PII
  — none should render raw values (SC-005).
